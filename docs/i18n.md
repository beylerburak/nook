# Internationalization

Nook ships in English (default/fallback) and Turkish. This is the guide for
converting a component's hardcoded strings to the `t()` API — the
infrastructure itself (this doc describes it) is already in place under
`apps/extension/src/i18n/`.

This module is Nook's own product-copy i18n. It is separate from Astryx's
built-in component strings ("Close" on a `Dialog`, date-picker labels, etc.),
which come from `@astryxdesign/core/i18n` and are wired up automatically by
`<I18nProvider>` (see "Astryx integration" below) — you never call `t()` for
those.

## Where messages live

- `apps/extension/src/i18n/locales/en.ts` — the source of truth. A nested,
  `as const` object, namespaced by area: `common`, `dashboard`,
  `settings.appearance`, etc. Add new namespaces as you convert new areas
  (`nav`, `search`, `bookmark`, `settings.ai`, …) — don't cram unrelated
  strings into an existing namespace.
- `apps/extension/src/i18n/locales/tr.ts` — the Turkish catalog. It's typed
  as `satisfies Messages` (derived from `en`), so **TypeScript fails to
  compile if you add a key to `en.ts` and forget it here** — add both in the
  same change.
- `apps/extension/src/i18n/types.ts` — the type machinery (`MessageKey`,
  `ParamsFor`, plural typing). You shouldn't need to touch this when just
  adding strings.
- `apps/extension/src/i18n/core.ts` — `translate()`, `resolveLocale()`,
  locale list. Non-React.
- `apps/extension/src/i18n/react.tsx` — `<I18nProvider>` / `useI18n()`.
- `apps/extension/lib/locale.ts` — persistence for the user's language
  *setting* (`"system" | "en" | "tr"`), mirroring `lib/appearance.ts`'s
  storage strategy exactly (see "Persistence" below).
- `apps/extension/src/i18n/index.ts` — the barrel; import from here
  (`import { useI18n } from "../../i18n"`, adjusting the relative path).

## Naming convention for keys

`<namespace>.<subNamespace?>.<camelCaseName>` — e.g.
`settings.appearance.modeLight`, `dashboard.itemCount`. Namespace by *area of
the app*, not by component file. Name the key after what the string means
(`languageRowDescription`), not after its English text.

## Using `t()`

Inside a component:

```tsx
import { useI18n } from "../../i18n"; // adjust the relative path to src/i18n

function MyPanel() {
  const { t } = useI18n();
  return <Text>{t("settings.appearance.modeLight")}</Text>;
}
```

`useI18n()` is best called under `<I18nProvider>` (already mounted in
`DashboardApp` and `PopupApp` — see "Mounting" below): that gets you a live,
reactive locale that updates instantly when the user changes it in Settings.
Called outside a provider (e.g. a component under test, rendered in
isolation) it still works — it falls back to a one-shot resolution from the
cached locale setting — but `setLocale` in that fallback only persists the
choice; it can't re-render the tree, since there's no provider state to
update.

`t(key, params?)` — `key` is type-checked against the full set of dot-paths
in `en.ts`; a typo or a key that doesn't exist is a compile error. See
`AppearancePanel.tsx` for a converted, working example (including the
language picker described below).

## Interpolation

A leaf message can contain `{name}`-style placeholders, filled from the
`params` object:

```ts
// en.ts
common: { greeting: "Hello, {name}" }

t("common.greeting", { name: "Ada" }); // "Hello, Ada"
```

An unmatched placeholder (missing from `params`) is left in the output
as-is, rather than throwing — treat that as a bug to fix, not a feature to
rely on.

## Plurals

A leaf can instead be a plural table, keyed by CLDR category
(`Intl.PluralRules`). English and Turkish both only ever produce `"one"` or
`"other"` (verified via `Intl.PluralRules('tr').select(n)` — Turkish nouns
don't inflect for plural the way English does, so `one` and `other` are
often the same string in `tr.ts`; still list both explicitly, don't rely on
a fallback):

```ts
// en.ts
dashboard: { itemCount: { one: "{count} saved item", other: "{count} saved items" } }

t("dashboard.itemCount", { count: 1 }); // "1 saved item"
t("dashboard.itemCount", { count: 3 }); // "3 saved items"
```

`count` is required (and type-checked as required) whenever a key resolves
to a plural table — `ParamsFor<K>` in `types.ts` enforces this. `count` is
also available as an ordinary `{count}` placeholder inside the chosen
string, as shown above.

## Dates and numbers

`useI18n()` also returns locale-aware formatters, so you don't reach for
`Intl.*` directly and get the wrong locale:

```tsx
const { formatDate, formatNumber, formatRelativeTime } = useI18n();
formatDate(new Date());                 // Intl.DateTimeFormat(locale).format(...)
formatNumber(1234.5);                   // Intl.NumberFormat(locale).format(...)
formatRelativeTime(-3, "day");          // Intl.RelativeTimeFormat(locale, {numeric:"auto"}).format(...)
```

Pass an `Intl.DateTimeFormatOptions` / `Intl.NumberFormatOptions` object as
a second argument the same way you would to the underlying `Intl` API.

## Non-React usage (content scripts, background, plain utilities)

`translate(locale, key, params)` from `src/i18n/core.ts` is the non-React
entry point — same type-checking as `t()`, just with an explicit `locale`
argument instead of reading it from context:

```ts
import { translate } from "../../i18n";
translate("tr", "common.greeting", { name: "Ada" });
```

To get the right `locale` to pass:

- **Same JS context as a mounted `<I18nProvider>`** (e.g. a plain helper
  called from dashboard code): `getActiveLocale()` from `src/i18n/react.tsx`
  (re-exported from the barrel) mirrors the active locale into a module
  variable whenever the provider resolves or changes it.
- **A different bundle/context — a content script** (`bookmark-toast.content.tsx`,
  `content/nook-button.ts`): these run on the host page's origin and don't
  share JS state with the extension pages, but they *can* see
  `chrome.storage.local`, which is where the setting is persisted. Read
  `readCachedLocaleSetting()` from `lib/locale.ts` (synchronous, best-effort)
  or `await loadLocaleSetting()` (authoritative), then
  `resolveLocale(setting)` to get a concrete `"en" | "tr"`, then `translate()`.
  This is the same pattern `lib/appearance.ts` already uses for the theme
  mode — `lib/locale.ts` mirrors it key-for-key. Converting the content
  scripts' own hardcoded strings to use this is left to the follow-up that
  converts their UI; the plumbing to read the locale there already works
  today.

## Locale resolution

`resolveLocale(setting, navigatorLanguage?)` (`src/i18n/core.ts`):

1. `setting === "en" | "tr"` → that locale, as-is.
2. `setting === "system"` (or anything else unrecognized) → falls through to
   `navigatorLanguage` (defaults to `navigator.language`): starts with
   `"tr"` (`tr`, `tr-TR`, …) → `"tr"`; anything else → `"en"`.

## Persistence

Stored exactly like the appearance/theme-mode preference
(`lib/appearance.ts`) — same reasoning: `chrome.storage.local` is the
source of truth because content scripts run on the host page's origin and
can't see the extension's own `localStorage`; extension pages additionally
keep a synchronous `localStorage` mirror so first paint doesn't flash the
wrong language. See `lib/locale.ts` (`loadLocaleSetting`,
`saveLocaleSetting`, `subscribeToLocaleSetting`, `readCachedLocaleSetting`).
Changing the language in Settings → Appearance applies live, immediately,
across every open surface (dashboard, popup) — no reload — the same way an
appearance-mode change does, via the same `chrome.storage.onChanged`
subscription mechanism.

`<I18nProvider>` also sets `document.documentElement.lang` whenever the
resolved locale changes.

## Astryx integration

`<I18nProvider>` wraps its children in Astryx's own
`<InternationalizationProvider locale={locale}>`
(`@astryxdesign/core/i18n`, see `apps/extension/AGENTS.md` →
`npx astryx docs internationalization`), so built-in Astryx component
strings follow the same locale. Astryx ships only an English catalog today;
for `"tr"` its runtime walks the locale chain and falls back to that
shipped `en` catalog for anything it doesn't have translated — this is
expected and requires no extra wiring on our side. If Astryx later ships a
first-party `tr` catalog, pass it via `messages={{ tr: trCatalog }}` on the
`InternationalizationProvider` in `src/i18n/react.tsx`.

## Mounting (already done — reference only)

`<I18nProvider>` is mounted in `DashboardApp` (`src/app/dashboard/DashboardApp.tsx`)
and `PopupApp` (`src/app/popup/PopupApp.tsx`), wrapping their whole tree
(including the Settings dialog, which renders inside `DashboardApp`). You
should not need to mount it again — just call `useI18n()` from any
component under either.

**apps/web**: the web app is out of scope for this change (it's being
restructured by another agent) but can reuse the same module — it lives in
`apps/extension/src/i18n/` and `apps/extension/lib/locale.ts`, both already
importable from `apps/web` the same way it imports the shared UI from
`../../extension/src/app`. To wire it up there, wrap the app root with:

```tsx
import { I18nProvider } from "../../extension/src/i18n";

<I18nProvider>
  <App />
</I18nProvider>
```

placed outermost (or at least outside anything that calls `useI18n()` —
in particular outside wherever the Settings dialog mounts).

## Turkish style guide

- Voice: informal-but-polite imperative — "Kaydet" (not "Kaydediniz" or
  "Lütfen kaydedin"), "Koleksiyon oluştur", "Değişiklikleri geri al". Pick
  this register consistently; don't mix in formal "-iniz" verb forms.
- Keep **"Nook"** untranslated everywhere, including mid-sentence.
- Use proper Turkish characters: ı İ ş ğ ü ö ç — never substitute plain
  ASCII look-alikes (`i` for `ı`/`İ`, `s` for `ş`, etc).
- Product terms — use these consistently, don't vary them:

  | English      | Turkish         |
  |--------------|-----------------|
  | bookmark     | yer imi         |
  | collection   | koleksiyon      |
  | tag          | etiket          |
  | library      | kütüphane       |
  | sync         | senkronizasyon  |
  | sign in      | giriş yap       |
  | sign out     | çıkış yap       |
  | settings     | ayarlar         |

- Plurals: Turkish nouns don't inflect for count — `"{count} yer imi"` is
  correct for both 1 and 5 (the numeral carries the plurality). Still fill
  in both `one` and `other` explicitly in `tr.ts` (see "Plurals" above) —
  don't omit `other` on the assumption it's identical; a future locale (or
  a reviewer skimming `tr.ts`) shouldn't have to guess that was intentional.
